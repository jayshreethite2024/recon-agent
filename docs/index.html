01 — The Problem

Every cycle, the same exceptions.

A rule-based reconciliation labels most rows automatically. The rows no rule can explain are left Unclassified — and analysts investigate each one by hand before the control can sign off.

Context
Expected vs. actual, every transaction

Each cycle, the recon compares expected ceded amounts (gross × treaty share) with what was actually posted, and labels rows: matched, in error, in retention, and so on.

The Gap
Unclassified rows need manual work

When no rule explains a variance, the row is left blank. An analyst has to dig through postings, codes and treaty documents to find out why — every cycle.

Why It Hurts
The same causes keep coming back

Mistyped company codes, postings that land a cycle late, treaty amendments not reflected in the system. The know-how lives in analysts' heads, not in a system.

The Constraint
It's a financial control

Any AI help must be explainable and auditable, and must never decide on its own. A confident wrong answer is worse than no answer at all.

02 — User & Goal

Start from evidence, not from zero.

The goal isn't to replace the analyst. It's to hand them a pre-investigated row with the facts already gathered.

Primary User
Recon analyst

Clears Unclassified rows each cycle under time pressure, before downstream sign-off.

Job To Be Done
"Show me why"

Give me the most likely cause and the facts behind it, so I can confirm or correct it quickly.

Non-Goal
Autonomous decisions

The agent suggests; the analyst decides. Nothing is closed automatically.

03 — The Product

An investigator. Not a chatbot.

It runs on every Unclassified row automatically — no prompts to write. For each row it decides which checks to run, reads the results, and submits a finding.

04 — Key Product Decisions

Six decisions that made it trustworthy.

DECISION 01
Narrow tools, not "run any SQL"

Four specific lookups are safer, auditable and easy to evaluate. A free SQL tool could run wrong or expensive queries.

DECISION 02
"Needs analyst" is a valid answer

For a financial control, honest uncertainty beats a confident guess. It's tracked as a safety metric, not a failure.

DECISION 03
Structured answer, not free text

The final answer is a tool with a fixed list of causes, evidence and confidence — measurable and consistent.

DECISION 04
Every step says why

Each tool call carries a one-line reason. Analysts see how it reached the answer, and every run leaves an audit trail.

DECISION 05
Cut what adds no evidence

I removed an error/retention tool on review: the recon already checks it, so it never found anything new. Fewer tools, better choices.

DECISION 06
The human always decides

The agent never closes a row. Accept/correct decisions become labels for monitoring and future improvement.

05 — Evaluation

Accuracy wasn't the real problem.

A test set of 50 Unclassified rows with known root causes — including 5 deliberately unclear cases where the right answer is "Needs analyst". Every run measures accuracy, per-cause precision and recall, confidence calibration, tool calls, cost and latency.

What 96% hid: both errors were unclear cases labelled "treaty amendment" with high confidence. Reading the traces, the agent's own evidence said no endorsement existed — and it labelled the row an amendment anyway.

My first hypothesis (a misleading search result) was wrong. It was a reasoning failure, not a retrieval one.
Fix 1
Stricter prompt

An amendment now needs an endorsement clause and numbers that match. A self-check before submitting, and defined confidence levels.

Fix 2
Code guardrail

If the agent says "amendment" but never retrieved an endorsement, code overrides it to "Needs analyst". Prompts can be ignored; code can't.

I re-ran the same 50 cases three times — once through the MCP server — to make sure the result was stable, not a lucky run.
06 — Trade-offs & Limits

What I chose not to do.

Cost
Safety over tokens

The v2 prompt is longer (+11% input tokens). Worth it to remove confidently-wrong answers.

Retrieval
No embeddings, yet

Planned as an upgrade, but evals showed keyword retrieval found 100% of amendment clauses. The failures were in reasoning, so I fixed that instead.

Architecture
No agent framework

A single agent with a simple loop is easier to debug and audit in plain code. I'd move to LangGraph for multi-agent handoffs or mid-run approvals.

Limits
Synthetic data

Five planted causes, one cause per row, 50 cases. Real exceptions are messier. The next proof point is anonymised real exceptions with analyst labels.

07 — PM Learnings

What this taught me about AI products.

1
The kind of error matters more than the error rate

96% looked good until I saw both errors were confident and wrong. Define the dangerous failure first, then measure it.

2
Read failures before fixing them

My first guess about the cause was wrong. Fixing on assumption would have targeted the wrong thing.

3
Design for "I don't know"

Giving the agent an honest way out made it safer and more useful, not less.

4
Layer your controls

A prompt shapes behaviour; a code guardrail enforces it. Finance has always worked this way.

5
Measure, then decide

Evals told me to skip embeddings and to use the cheaper, faster model. Neither was my starting assumption.

08 — What's Next

From demo to control.

Real-data pilot

Anonymised exceptions with analyst labels; track accept rate and time per row.

Labels → ML classifier

Accepted and corrected findings train a cheaper model for the common patterns.

Patterns → rules

Reliable patterns graduate into deterministic recon rules, shrinking the Unclassified bucket.

Messier cases

Multiple causes per row, an "Other" category, and hybrid search for long treaties.
